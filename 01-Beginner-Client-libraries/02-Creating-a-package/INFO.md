## 1. ament as Build System, colcon as Build Tool, and Other Build Types

### The Roles of ament and colcon

Two tools work together every time you run `colcon build`.

**ament** is the  **build system framework** . It provides the CMake modules and Python packaging extensions that ROS 2 packages use to describe themselves, find dependencies, and install their outputs. Think of ament as the *standard format and rulebook* that packages are written in. It comes in two flavours: `ament_cmake` for C++ and `ament_python` for Python.

**colcon** is the **build tool** — the outer orchestrator. It discovers packages by reading their `package.xml` files, determines a build order from their dependencies, and then invokes the appropriate ament build system for each package. colcon itself does not compile code; it delegates to ament_cmake (which calls CMake and Make) or to ament_python (which calls setuptools).

A useful analogy: ament is a **recipe format standard** that every cook follows. colcon is the **head chef** who reads each recipe card in dependency order and sends it to the appropriate kitchen (the C++ kitchen or the Python kitchen) to be cooked.

The full call chain for a CMake package is:

```text
colcon build
  └─ reads package.xml via colcon-ros plugin
  └─ calls cmake (driven by ament_cmake CMake modules)
       ├─ CMake configures the build, runs find_package()
       ├─ Make compiles .cpp → .o → binary
       └─ cmake --install copies outputs into install/
```

For a Python package:

```text
colcon build
  └─ reads package.xml via colcon-ros plugin
  └─ calls pip install -e / setup.py develop (via ament_python)
       ├─ setuptools registers entry points
       └─ data files (package.xml, ament markers) installed into install/
```

### Other Build Types

Beyond `ament_cmake` and `ament_python`, other build types exist:

| Build type       | Status           | Use case                                           |
| ---------------- | ---------------- | -------------------------------------------------- |
| `ament_cmake`    | Official, Tier 1 | C++ ROS 2 packages                                 |
| `ament_python`   | Official, Tier 1 | Python ROS 2 packages                              |
| `cmake`          | Supported        | Non-ROS C++ libraries wrapped into a ROS workspace |
| `ament_cargo`    | Community        | Rust packages via the ros2_rust project            |
| `meson`          | Experimental     | Meson build system packages                        |

**Is Rust one of them?** Yes. The `ros2_rust` project provides an `ament_cargo` build type that lets you write ROS 2 nodes in Rust. When you declare `<build_type>ament_cargo</build_type>` in `package.xml`, colcon uses a plugin that calls Cargo (Rust's build tool) instead of CMake or setuptools. However, it is **not an officially supported Tier 1 build type** — it is a community project maintained separately from the ROS 2 core. For all learning and production ROS 2 work, use `ament_cmake` or `ament_python`.

The pure `cmake` type (without ament) is useful when you want to include a third-party C++ library that has its own CMakeLists.txt but does not know about ROS 2 conventions. You put it in your workspace, declare `<build_type>cmake</build_type>`, and colcon builds it as a plain CMake project.

## 2. CMake vs Python Packages — Side-by-Side Comparison

### File Structure

| Aspect               | ament_cmake                        | ament_python                                                     |
| -------------------- | ---------------------------------- | ---------------------------------------------------------------- |
| Build config         | `CMakeLists.txt`                   | `setup.py`+`setup.cfg`                                           |
| Source code          | `src/my_node.cpp`                  | `my_package/my_node.py`                                          |
| Public headers       | `include/my_package/`              | (not applicable)                                                 |
| Package identity     | `package.xml`                      | `package.xml`AND `setup.py`(must match)                          |
| ament marker         | (generated by CMake at build time) | `resource/my_package`(explicit empty file)                       |
| Python module dir    | (not applicable)                   | `my_package/`inner dir with `__init__.py`                        |
| Auto-generated tests | Via CMakeLists.txt + ament_lint    | `test/test_copyright.py`,`test_flake8.py`,`test_pep257.py`       |

### Directory Layout

**CMake package:**

```text
my_cmake_package/
├── CMakeLists.txt
├── include/
│   └── my_cmake_package/    ← public C++ headers (for other packages to use)
├── package.xml
└── src/
    └── my_node.cpp          ← C++ source code
```

**Python package:**

```text
my_python_package/
├── package.xml
├── resource/
│   └── my_python_package    ← empty ament discovery marker file
├── setup.cfg
├── setup.py
├── test/
│   ├── test_copyright.py
│   ├── test_flake8.py
│   └── test_pep257.py
└── my_python_package/       ← Python module (same name as the package)
    ├── __init__.py
    └── my_node.py           ← Python source code
```

### What Each File Does

**`CMakeLists.txt`** is the CMake build script. It declares what to compile, what libraries to link, and what to install into `install/`. colcon reads `package.xml` to detect ament_cmake and then drives CMake using this file.

**`include/my_cmake_package/`** holds C++ header files that other packages are allowed to use (the public API). Headers used only internally within this package go in `src/` alongside the `.cpp` files.

**`setup.py`** is the Python installation script. It defines entry points (which turn Python functions into `ros2 run`-able executables), data files to install, and package metadata. It is the Python equivalent of CMakeLists.txt in terms of controlling installation.

**`setup.cfg`** contains the `[develop]` and `[install]` settings that tell `ros2 run` and ament where executable scripts are located. Without it, `ros2 run my_python_package my_node` would not find the node entry point.

**`resource/my_python_package`** is an empty file. When installed to `install/share/ament_index/resource_index/packages/my_python_package`, it acts as a registry entry. Tools like `ros2 pkg list` scan this directory to discover what packages are installed. CMake packages generate this marker automatically during their cmake install step, so the explicit source file is only needed for Python packages.

**`my_python_package/__init__.py`** makes the inner directory a proper Python module importable as `import my_python_package`. Without it, Python would not treat the directory as a package.

### Language and Compilation

CMake packages compile at build time. `colcon build` invokes `g++` on your `.cpp` files and produces a native binary. The binary is installed to `install/my_cmake_package/lib/my_cmake_package/my_node`. When you run it, no interpreter is needed — it runs directly on the CPU.

Python packages do not compile at build time. `colcon build` registers entry points and copies/symlinks data files. The `.py` source files remain as text. Running the entry point via `ros2 run` starts the Python interpreter at runtime and calls the `main` function registered in `setup.py`.

## 3. Nested Packages — Why Forbidden, and How `src/` Keeps Things Clean

### Why Nested Packages Are Forbidden

colcon discovers packages by recursively scanning directories for `package.xml` files. When it finds one, it treats the entire directory as belonging to that package and  **stops crawling deeper into that directory** . This is intentional — the package directory is the unit of isolation.

If you tried to nest a package inside another:

```text
my_outer_package/
├── package.xml          ← colcon finds this and claims the entire directory
├── CMakeLists.txt
└── my_inner_package/
    └── package.xml      ← colcon never reaches this; crawl stopped above
```

The inner `package.xml` would never be discovered. Even if colcon could somehow see both, the CMake build of the outer package would have no structured way to treat the inner directory as a separate build unit. Their `install/` prefixes would overlap, causing file conflicts and broken `find_package()` calls from other packages.

The correct pattern is for every package to be a sibling directory directly under `src/`. Packages can depend on each other via `<depend>` tags in `package.xml` but must never contain each other on the filesystem.

### How `src/` Keeps the Workspace "Clean"

When you run `colcon build`, it creates `build/`, `install/`, and `log/` alongside wherever it is invoked from. Without a `src/` subdirectory, your workspace root would look like:

```text
ros2_ws/                    ← you run colcon from here
├── my_cmake_package/       ← source
├── my_python_package/      ← source
├── build/                  ← generated
├── install/                ← generated
└── log/                    ← generated
```

Source code and generated artifacts are all at the same level, making it unclear what is yours and what colcon produced. colcon must crawl `build/` and `install/` (using `COLCON_IGNORE` and `AMENT_IGNORE` markers inside them to stop) just to confirm they are not packages.

With `src/`:

```text
ros2_ws/
├── src/                    ← ONLY your source packages live here
│   ├── my_cmake_package/
│   └── my_python_package/
├── build/                  ← generated, clearly separate
├── install/                ← generated, clearly separate
└── log/                    ← generated, clearly separate
```

colcon only crawls `src/` for package discovery. Everything at the root level is either the `src/` directory (which colcon crawls) or a known generated directory (which colcon skips entirely). Git, editors, and humans can immediately understand the layout: `src/` is what you author, everything else is disposable output that should be in `.gitignore`.

A realistic workspace with mixed package types looks like:

```text
workspace_folder/
└── src/
    ├── cpp_package_1/
    │   ├── CMakeLists.txt
    │   ├── include/cpp_package_1/
    │   ├── package.xml
    │   └── src/
    ├── py_package_1/
    │   ├── package.xml
    │   ├── resource/py_package_1
    │   ├── setup.cfg
    │   ├── setup.py
    │   └── py_package_1/
    └── cpp_package_n/
        ├── CMakeLists.txt
        ├── include/cpp_package_n/
        ├── package.xml
        └── src/
```

colcon handles all of these in one `colcon build` invocation from `workspace_folder/`, building them in correct dependency order regardless of whether they are C++ or Python.

## 4. With vs Without Optional Arguments — And Manual Substitution

### Comparison at Creation Time

**Without any optional arguments:**

```bash
ros2 pkg create my_package
```

This defaults to `ament_cmake`, sets `<license>TODO</license>`, creates no node source file, and the maintainer field depends entirely on whether git is globally configured. The result is a skeleton CMake package with no code to run.

**With the full set of optional arguments:**

```bash
ros2 pkg create --build-type ament_cmake --license Apache-2.0 --node-name my_node my_package
```

This additionally creates `src/my_node.cpp` with a compilable Hello World, writes `Apache-2.0` into `package.xml`, and downloads the full Apache 2.0 license text into a `LICENSE` file at the package root.

### What Each Argument Controls

|Argument          |Default if omitted                                           |Effect                                                                          |
|------------------|-------------------------------------------------------------|--------------------------------------------------------------------------------|
|`--build-type`    |`ament_cmake`                                                |Selects the cmake or python package template entirely                           |
|`--license`       |`TODO: License declaration`in `package.xml`, no `LICENSE`file|Sets `<license>`tag and creates the `LICENSE`text file                          |
|`--node-name`     |(no node created)                                            |Creates a Hello World source file, wires it into CMakeLists.txt or setup.y      |
|`--dependencies`  |`[]`                                                         |Adds `<depend>`tags to `package.xml`and `find_package()`calls to CMakeLists.txt |
|`--package-format`|`3`                                                          |Selects which `package.xml`format version to use                                |

### Manual Substitution If You Skip the Flags

**Substituting `--build-type ament_python` after the fact:**

If you ran `ros2 pkg create my_package` (defaults to cmake) but wanted Python, you would need to manually delete `CMakeLists.txt`, `include/`, and `src/`, then create `setup.py`, `setup.cfg`, `resource/my_package`, and the inner `my_package/__init__.py`, and edit `package.xml` to remove the cmake buildtool_depend and change the export build_type. It is far easier to use the flag correctly from the start.

**Substituting `--license Apache-2.0` manually:**

Edit `package.xml` and change the license tag, then manually copy the Apache 2.0 license text into a `LICENSE` file at the package root.

```xml
<!-- Change this: -->
<license>TODO: License declaration</license>

<!-- To this: -->
<license>Apache-2.0</license>
```

**Substituting `--node-name my_node` manually for a CMake package:**

Create `src/my_node.cpp`:

```cpp
#include <cstdio>

int main(int argc, char ** argv)
{
  (void) argc;
  (void) argv;
  printf("hello world my_package package\n");
  return 0;
}
```

Then add these lines to `CMakeLists.txt`:

```cmake
add_executable(my_node src/my_node.cpp)
install(TARGETS my_node DESTINATION lib/${PROJECT_NAME})
```

**Substituting `--node-name my_node` manually for a Python package:**

Create `my_package/my_node.py`:

```python
def main():
    print('Hi from my_package.')

if __name__ == '__main__':
    main()
```

Then add this entry to the `entry_points` section of `setup.py`:

```python
entry_points={
    'console_scripts': [
        'my_node = my_package.my_node:main'
    ],
},
```

## 5. Package Format — Versions, Features, and What It Affects

### What Package Format Means

The `format` attribute in `<package format="3">` declares which REP (ROS Enhancement Proposal) specification version the `package.xml` file conforms to. Each format version introduced new XML tags and capabilities. Tools that read `package.xml` — colcon, rosdep, bloom, catkin_pkg — use the format number to know which tags are valid and how to interpret them.

The format number affects  **only `package.xml`** . It has no effect on the directory structure of your package, your CMakeLists.txt, your Python source files, or your setup.py. It is purely a schema version for the metadata file.

### The Three Formats

**Format 1 — REP 127 (legacy, avoid for ROS 2):**

The original catkin/ROS 1 format. Dependency tags are split into separate build and runtime entries with no combined shorthand:

```xml
<package>
  <build_depend>rclcpp</build_depend>
  <run_depend>rclcpp</run_depend>
  <!-- No combined <depend> tag exists -->
</package>
```

Not recommended for any new ROS 2 package. Included here only for historical context.

**Format 2 — REP 140 (older ROS 2 packages):**

Introduced the combined `<depend>` tag (build + runtime at once) and explicit `<exec_depend>` and `<build_export_depend>` tags:

```xml
<package format="2">
  <depend>rclcpp</depend>                         <!-- build + exec combined -->
  <build_export_depend>my_msgs</build_export_depend>
  <exec_depend>some_runtime_lib</exec_depend>
</package>
```

Still valid and used by many existing ROS 2 packages, but superseded by format 3.

**Format 3 — REP 149 (current standard):**

Adds conditional dependencies and group dependencies. This is what `ros2 pkg create` generates by default:

```xml
<package format="3">
  <depend>rclcpp</depend>

  <!-- Conditional: only on Windows -->
  <depend condition="$ROS_OS_OVERRIDE == 'windows'">windows_sdk</depend>

  <!-- Group: depend on an entire named group of packages -->
  <group_depend>my_sensor_drivers</group_depend>
</package>
```

Always use format 3 for any new package.

### The `--package-format` Argument

`ros2 pkg create` accepts `--package-format` to specify the format explicitly:

```bash
ros2 pkg create --build-type ament_cmake --package-format 3 my_package
# ↑ redundant since 3 is already the default, but valid
```

There is almost never a reason to pass `--package-format 1` or `--package-format 2` unless you are maintaining a legacy package that must remain compatible with very old ROS tooling.

### Summary of What Format Affects vs Does Not Affect

| Affected by format                                          | Not affected by format             |
| ----------------------------------------------------------- | ---------------------------------- |
| Which XML tags are valid in `package.xml`                   | Directory structure of the package |
| Dependency tag syntax (`<depend>`vs `<run_depend>`)         | CMakeLists.txt content             |
| Availability of `condition`attribute for conditional deps   | setup.py / setup.cfg content       |
| Availability of `<group_depend>`and `<member_of_group>`     | Source code (.cpp or .py files)    |

## 7. package.xml and setup.py — Line-by-Line Explanation and Why They Must Match

### The XML Header Lines (Both Packages)

```xml
<?xml version="1.0"?>
```

The standard XML declaration. Tells any XML parser that this file follows the XML 1.0 specification. Required at the top of every `package.xml`.

```xml
<?xml-model href="http://download.ros.org/schema/package_format3.xsd"
            schematypens="http://www.w3.org/2001/XMLSchema"?>
```

An XML processing instruction linking the file to a validation schema. XML-aware editors (VS Code with the XML extension) download this schema and use it to validate your `package.xml` in real time, highlighting unknown tags or missing required fields. This line does not affect how colcon reads the file at runtime; it is purely for development-time editor validation.

### CMake `package.xml` — Every Tag Explained

```xml
<package format="3">
```

The root element. `format="3"` specifies the REP 149 specification, enabling `<depend>`, conditional dependencies, and group dependencies.

```xml
<name>my_cmake_package</name>
```

The canonical package name. Must exactly match the directory name in `src/`, the `project()` call in CMakeLists.txt, and the first argument in `ros2 run my_cmake_package my_node`.

```xml
<version>0.0.0</version>
```

Semantic version number. Used by release tools (bloom) and by `find_package()` version checks when other packages declare a dependency on this one with a minimum version.

```xml
<description>Beginner client libraries tutorials practice package</description>
```

Human-readable description. Appears in `ros2 pkg list --verbose` and in generated package documentation.

```xml
<maintainer email="abdullah.reda44@gmail.com">abdullah</maintainer>
```

Identifies who is responsible for this package. Required for releasing to the ROS package index. colcon and rosdep do not use this field during builds; it is metadata for humans and release tooling.

```xml
<license>Apache-2.0</license>
```

Declares the distribution license. Required for any public release. Apache-2.0 is a permissive open-source license commonly used for robotics code.

```xml
<buildtool_depend>ament_cmake</buildtool_depend>
```

Declares that the ament_cmake package must be present at build time to drive the CMake build. This is what causes colcon's `colcon-ros` plugin to activate the `colcon-cmake` build backend. Python packages have no equivalent tag — they have no CMake build system.

```xml
<test_depend>ament_lint_auto</test_depend>
<test_depend>ament_lint_common</test_depend>
```

Dependencies needed only during testing. `ament_lint_auto` automatically selects which linters to run based on what is installed. `ament_lint_common` is the standard C++ linter set: copyright header checking, cppcheck static analysis, cpplint Google-style checking, and uncrustify formatting.

```xml
<export>
  <build_type>ament_cmake</build_type>
</export>
```

The tag colcon's `colcon-ros` plugin reads to decide which build plugin to activate. `ament_cmake` triggers the CMake-based build. `ament_python` triggers the setuptools-based build. Without this tag, colcon cannot determine how to build the package and will skip it.

### Python `package.xml` — Key Differences from CMake

There is no `<buildtool_depend>` tag. Python packages have no CMake build tool. Their entire build is driven by setuptools via `setup.py`, and ament_python is invoked by colcon's Python plugin, not declared as a buildtool dependency.

The test dependencies are Python-specific:

```xml
<test_depend>ament_copyright</test_depend>
<test_depend>ament_flake8</test_depend>
<test_depend>ament_pep257</test_depend>
<test_depend>python3-pytest</test_depend>
```

`ament_copyright` checks Python file copyright headers. `ament_flake8` runs the PEP8 style checker. `ament_pep257` checks docstring conventions. `python3-pytest` is the test runner that executes all files in the `test/` directory.

### `setup.py` — Every Field Explained

```python
package_name = 'my_python_package'
```

A Python variable used as a single source of truth for the package name within `setup.py`. All other occurrences use this variable, so renaming the package only requires changing this one line.

```python
packages=find_packages(exclude=['test']),
```

`find_packages()` scans the package directory for subdirectories containing `__init__.py` and treats each as an installable Python module. `exclude=['test']` prevents the `test/` directory from being registered as a Python package — tests are never meant to be importable by external code.

```python
data_files=[
    ('share/ament_index/resource_index/packages',
        ['resource/' + package_name]),
    ('share/' + package_name, ['package.xml']),
],
```

Non-Python files that must be installed alongside the Python code. The first entry installs the empty ament marker file to `install/share/ament_index/resource_index/packages/my_python_package`, which is how `ros2 pkg list` and other ament tools know this package is installed. The second entry copies `package.xml` to `install/share/my_python_package/package.xml`, making it available at runtime for tools like `ros2 pkg xml`.

```python
install_requires=['setuptools'],
```

Python packaging dependencies required at install time. `setuptools` itself is the only requirement for a minimal package. Runtime ROS dependencies (like `rclpy`) would also appear here but are not needed for this Hello World.

```python
entry_points={
    'console_scripts': [
        'my_node = my_python_package.my_node:main'
    ],
},
```

This is the critical registration that makes `ros2 run my_python_package my_node` work. It instructs setuptools to create a runnable script named `my_node` that, when executed, imports `my_python_package.my_node` and calls its `main` function. The format of each entry is `'executable_name = python.module.path:function_name'`. The installed script ends up at `install/my_python_package/lib/my_python_package/my_node`.

### Why `package.xml` and `setup.py` Must Match Exactly

The same metadata fields appear in both files:

| Field        | In `package.xml`                            | In `setup.py`                                  |
| ------------ | ------------------------------------------- | -----------------------------------------------|
| Package name | `<name>my_python_package</name>`            | `name=package_name`                            |
| Version      | `<version>0.0.0</version>`                  | `version='0.0.0'`                              |
| Description  | `<description>...</description>`            | `description='...'`                            |
| Maintainer   | `<maintainer email="...">name</maintainer>` | `maintainer='name'`,`maintainer_email='...'`   |
| License      | `<license>Apache-2.0</license>`             | `license='Apache-2.0'`                         |

They must match because the two files serve different audiences consuming the same package.

`package.xml` is read by colcon, rosdep, bloom, and the ROS package index — the build, dependency resolution, and release toolchain. These tools operate at the ROS workspace and distribution level.

`setup.py` is read by setuptools and pip — the Python packaging ecosystem. When someone installs your package with `pip install` (bypassing colcon entirely), only `setup.py` is consulted. When colcon builds, it reads both.

If the two files disagree — say `package.xml` says version `0.0.0` but `setup.py` says `1.0.0` — then `ros2 pkg xml my_python_package` reports `0.0.0` while `pip show my_python_package` reports `1.0.0`. This inconsistency confuses debugging, breaks release automation, and causes rosdep dependency resolution errors. The auto-generated `test_copyright.py` test suite includes a check for this mismatch and will fail `colcon test` if the files disagree.

## 8. Full Commands — All Steps in One Reference Block

```bash
# ─── PREREQUISITES ───────────────────────────────────────────────────────────
# Source ROS 2 Jazzy in your build terminal:
source /opt/ros/jazzy/setup.bash

# Create the workspace and navigate to src/:
mkdir -p ~/ros2_ws/src
cd ~/ros2_ws/src

# ─── CREATE PACKAGES ─────────────────────────────────────────────────────────

# CMake (C++) package with a Hello World node and license:
ros2 pkg create --build-type ament_cmake --license Apache-2.0 --node-name my_node my_cmake_package

# Python package with a Hello World node and license:
ros2 pkg create --build-type ament_python --license Apache-2.0 --node-name my_node my_python_package

# Minimal package (no node, no license, defaults to ament_cmake):
ros2 pkg create my_package

# Package with declared ROS dependencies:
ros2 pkg create --build-type ament_cmake --license Apache-2.0 \
  --dependencies rclcpp std_msgs --node-name my_node my_dep_package

# Package with explicit format version (3 is default, rarely needed):
ros2 pkg create --build-type ament_cmake --package-format 3 my_package

# ─── BUILD ───────────────────────────────────────────────────────────────────
# Return to workspace root:
cd ~/ros2_ws

# Build all packages in the workspace:
colcon build

# Build only one specific package (assumes dependencies already built):
colcon build --packages-select my_cmake_package

# Build a package and all its dependencies:
colcon build --packages-up-to my_cmake_package

# Build with symlink install (Python edits take effect without rebuild):
colcon build --symlink-install

# Build with live terminal output instead of buffered log:
colcon build --event-handlers console_direct+

# Build one package at a time (useful on slow hardware):
colcon build --executor sequential

# ─── SOURCE THE WORKSPACE ────────────────────────────────────────────────────
# Open a new terminal, then:
source /opt/ros/jazzy/setup.bash
cd ~/ros2_ws
source install/local_setup.bash

# ─── RUN THE PACKAGES ────────────────────────────────────────────────────────
ros2 run my_cmake_package my_node
# Output: hello world my_cmake_package package

ros2 run my_python_package my_node
# Output: Hi from my_python_package.

# ─── INSPECT PACKAGES ────────────────────────────────────────────────────────
# List all ROS 2 packages visible in the current environment:
ros2 pkg list

# View the package.xml of an installed package:
ros2 pkg xml my_cmake_package

# Show the install prefix of a package:
ros2 pkg prefix my_cmake_package

# Inspect generated file structures:
ls src/my_cmake_package/
ls src/my_python_package/
ls src/my_python_package/my_python_package/

# ─── COLCON_IGNORE QUICK REFERENCE ───────────────────────────────────────────
# Temporarily exclude a package from builds:
touch src/my_cmake_package/COLCON_IGNORE

# Re-enable it:
rm src/my_cmake_package/COLCON_IGNORE
```
